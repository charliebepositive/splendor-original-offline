# Android 平板离线移植方案：Y900 13（2026）

日期：2026-09-05。状态：已实现 Android 离线容器、私有目录原子存档及系统文件导入/导出，已生成签名 APK 1.0.0。构建、lint、签名、包对齐及 90 张卡面完整性检查通过；横竖屏、分屏与存档流程已完成浏览器模拟接口验证。尚未连接 Y900 真机，真机验收待完成。实际实现与构建步骤见根目录 `android/README.md`；下文保留移植设计和真机验收目标。

## 推荐路线

采用 **Kotlin 轻量 Android 容器 + 系统 WebView + AndroidX WebViewAssetLoader + 现有 HTML/CSS/JavaScript 游戏**。输出可直接安装的签名 APK，全部游戏资源随安装包提供，安装后首次打开即可断网运行。

本次只面向 Android 离线游戏，原生容器所需能力有限：资源加载、存档、导入导出、返回键、窗口尺寸与生命周期。该路线可以直接复用当前游戏逻辑，同时减少新的框架依赖。若未来明确同时发布 iOS，再评估 Capacitor；当前无需为此提前增加跨平台运行时。

## 当前架构核对

当前 `splendor-original` 的运行时为普通 HTML/CSS/JavaScript，未依赖 Python：

| 文件 | 职责 | Android 处理 |
| --- | --- | --- |
| `js/engine.js` | 规则、状态转换、存档校验 | 复用，继续运行现有规则测试 |
| `js/ai.js` | 本地启发式 AI | 复用；生命周期暂停，必要时迁入 Worker |
| `js/data.js` | 90 张发展卡、10 位贵族 | 复用 |
| `js/ui.js` | DOM 渲染、交接、存档与操作 | 拆出平台适配接口，改平板交互 |
| `css/style.css` | 现有桌面/手机响应式样式 | 增加按宽度和高度共同决策的平板布局 |
| `assets/cards` | 90 张 630×880 PNG | APK 内置；可另生成压缩版本并核对字迹 |
| `sw.js` | 浏览器离线缓存 | 浏览器版保留，APK 环境不注册 |
| `tools/serve.cjs` | 可选 Node 本地静态服务 | 不打入 APK，不启动服务进程 |

若在 PC 使用 `python -m http.server`，Python 仅负责发送静态文件。参考 Pokémon 项目中的 Python 文件属于 AI 训练工具，不是当前原版游戏的浏览器运行时。因此没有必要把 Python 解释器或训练环境移入 Android。

## 目标设备

用户确认设备为 **联想拯救者 Y900 13、2026 款**。联想官方资料对应 **TB522FU、13 英寸、3840×2560、3:2、Android 16**。

- [联想官方规格](https://item.lenovo.com.cn/product/1054307.html)
- [联想官方用户指南索引，2026-05-25](https://iknow.lenovo.com.cn/detail/440350?keyWordId=&keyword=&type=0)
- [联想官方 3:2 屏幕说明](https://iknow.lenovo.com.cn/detail/440439?keyWordId=&keyword=&type=0)

适配以 **3:2 横屏桌面** 为主，同时支持竖屏、分屏和电脑模式窗口。3840×2560 是物理像素，不等于 WebView 的 CSS 视口。设计时可用 1440×960 CSS px 作为归一化参考画布，但不将其假定为真机实际视口，更不固定 DPR。

真机启动时记录可用窗口、WebView 视口、`devicePixelRatio`、系统栏安全区域与字体/显示缩放设置。布局根据实际容器宽高计算。

## APK 结构与离线方式

```text
Android 安装包
├─ Kotlin Activity / WebView
├─ WebViewAssetLoader → assets/www/index.html
├─ assets/www/{js,css,assets,docs} → 同一份游戏资源
└─ 原生平台接口
   ├─ 应用私有目录 JSON 存档
   ├─ 系统文件选择器：导入/导出
   ├─ 返回键与前后台通知
   └─ 窗口安全区域与尺寸变化
```

使用 `https://appassets.androidplatform.net/assets/www/index.html` 作为应用内资源地址，实际由 WebViewAssetLoader 从 APK 读取。它不代表远程站点，不需要本地 TCP 服务器，也不依赖第一次联网缓存。

配置 Android 构建环境标记，使 APK 不注册 Service Worker，避免 APK 资源与旧缓存混用。静态资源按白名单复制，排除测试、源数据、开发服务器与浏览器验证目录。

仅加载内置页面；原生消息接口只接受该本地来源的主框架请求。未命中的内部资源返回明确错误，不回退远程加载。本应用运行不申请 INTERNET 权限；来源链接如需访问可交给外部浏览器。

依据：[Android 官方：加载应用内 Web 内容](https://developer.android.com/develop/ui/views/layout/webapps/load-local-content)。

## 自适应桌面

Y900 横屏的布局目标是：**三级市场 12 张卡、最多 5 位贵族、公共筹码和本回合确认按钮同时可见**。历史记录、已购卡详情及非当前玩家的完整面板可在局部展开，不挤压主市场。

横屏建议分区：

| 区域 | 内容与约束 |
| --- | --- |
| 顶部窄栏 | 当前玩家、轮次、最后一轮提示、规则/菜单 |
| 左侧主桌面 | 顶部贵族，下面三级市场；每级牌堆 + 4 张明牌 |
| 右侧约 26%–30% | 当前玩家筹码与折扣、保留牌，其余玩家分数/折扣摘要 |
| 主桌面底部 | 6 色公共筹码、选取数量、确认/取消 |

不直接将当前整页等比例缩小。现有最大宽度 1120px、侧栏 240/286px、卡高上限 180px及较多 9–12px 文字，需要调整。

建议初始断点如下；它们是本项目 CSS 设计值，不是 Android 官方 dp 分类，落地后由真机测试校准：

| 可用视口 | 模式 |
| --- | --- |
| 横屏，宽 ≥1100 CSS px 且高 ≥720 | 完整桌面；固定可达的操作区；玩家详情仅局部滚动 |
| 横屏但较窄或较矮 | 压缩标题与贵族留白；其他玩家变摘要；手牌与日志采用抽屉 |
| 竖屏且宽 ≥600 CSS px | 市场仍保持每级 4 张；玩家详情移到下方/抽屉；底部保留操作入口 |
| 窗口宽 <600 CSS px | 紧凑模式；允许内容纵向滚动与卡牌放大，避免强行缩成难以点击的一屏 |

使用 Grid、`minmax()`、`clamp()` 和容器尺寸观察。外层 `100dvh` 管理可用高度，接收原生 WindowInsets，避免系统手势条或任务栏覆盖按钮。横屏优先设计，同时允许旋转和窗口缩放；尺寸变化只重排界面，不重新创建对局。

卡牌尺寸同时受宽、高约束：

```text
每行可用卡宽 = (市场宽度 − 牌堆宽度 − 横向间隔) / 4
每行可用卡高 = (市场高度 − 两个行间隔) / 3
最终卡高 = min(每行可用卡高, 每行可用卡宽 × 880 / 630)
最终卡宽 = 最终卡高 × 630 / 880
```

尺寸低于易读阈值时，切换紧凑布局或启用局部滚动，不能继续无限缩小。卡面保留原比例。分数、折扣、支付数字等关键内容使用 DOM/SVG 展示或在详情中补充，使 4K 屏上的文字清晰可读；不通过图片放大假装增加原画细节。

依据：[Android WebView 屏幕与视口说明](https://developer.android.com/develop/ui/views/layout/webapps/targeting)。

## 平板触控交互

- 主要按钮以 48–56 CSS px 起步，在真机默认视口下按至少 48dp 的触摸目标校准；筹码可做 56–64 CSS px，控件间留 8–12px。
- 卡牌轻触打开大图、折扣后价格与购买/保留按钮，不依赖悬停。保留黄金调整支付功能。
- 取不同色与取同色双枚提供明确模式/数量反馈，减少当前反复点击循环选择的学习成本。
- 点击确认后立即锁定本次提交，等待规则处理和存档确认，防止连点导致多步行动。
- 多人热座继续遮挡手牌；切后台再恢复时先显示交接遮挡。四人局所有人的公开分数与折扣摘要始终可查。
- 返回键依次关闭详情、关闭可取消菜单、进入暂停界面；归还筹码和贵族选择等必选阶段不能被跳过。

## 存档与生命周期

新增 `platform.js`，向 UI 提供 `loadGame/saveGame/importGame/exportGame/onPause/onResume` 等统一接口。PC 继续使用 localStorage 与浏览器下载；Android 改用原生实现，游戏 JSON 和 `version` 保持兼容。

Android 保存完整对局 JSON 至应用私有目录，以串行写入、递增修订号及原子替换避免半写入和旧状态覆盖新状态。关键行动的保存成功回执返回后，才宣布该行动已持久化并调度下一次 AI。保留可恢复备份，导入时先调用现有规则校验，失败不覆盖当前对局。

导入/导出接 Android Storage Access Framework 系统文件选择器，允许用户保存到自己选择的位置，无需让用户寻找应用私有目录。不要依赖 WebView 自动支持当前 `blob:` 下载链接。

切后台、锁屏时停止 AI 定时器和新行动；恢复时读取同一回合/阶段，最多安排一个 AI 操作。Activity 重建或进程被回收后恢复最近已确认存档，包括 `return`、`noble` 中间阶段，不能重复执行拿牌/购买。

应用升级使用固定包名与同一签名证书，并维护存档迁移。卸载或清除应用数据会删除私有存档，跨设备迁移使用 JSON 导出。

依据：[Android AtomicFile](https://developer.android.com/reference/android/util/AtomicFile)、[系统文件选择器](https://developer.android.com/training/data-storage/shared/documents-files)。

## 资源与运行性能

当前 90 张 PNG 共约 55.4 MB，可完整打包，资源体积主要来自图片。第一版优先保持画面；若做 WebP 衍生资源，应逐张核对成本数字，并以实际构建结果报告压缩收益。

资源在安装包内可用不等于启动时要全部解码。只创建市场、手牌和当前详情所需图片；不同时预解码 90 张大图。APK 不额外将全部图片复制到 Service Worker 缓存。

现有 AI 是回合制启发式计算。先在 Y900 WebView 测量决策耗时和主线程长任务；出现可感知卡顿时将 AI 放入 Web Worker，携带状态修订号，丢弃过期结果。无需为了支持 4K 高刷新率屏幕建立持续游戏循环，静止桌面按事件更新。

默认离线规则入口继续使用现有中文 HTML。官方 PDF 内置并允许通过系统文件接口导出，不把完整规则阅读依赖于外部 PDF 阅读器。

## 实施顺序与交付

1. 改造 Web 平板布局，完成 Y900 3:2 横屏、竖屏和窄窗口验证；保留 PC 运行方式。
2. 添加独立 `android/` 容器工程，构建时复制同一份 Web 资源，保证全新安装首次断网可用。
3. 接入平台存档、文件选择器、返回键和生命周期；验证 PC 与 Android 之间 JSON 互导。
4. 在真实 Y900 13（TB522FU）测试并打包签名 APK，同时交付源码和构建说明。

验收至少包含：飞行模式首次启动与完整对局；2/3/4 人热座及 AI；120 局已有规则回归；横竖屏与分屏反复切换；字体/显示缩放；连点；AI 思考时锁屏；在归还和贵族选择阶段强制结束进程再恢复；升级保留存档；系统文件选择器导入/导出；4K 卡面清晰度与触摸命中。

设计稿/浏览器设备模拟仅验证布局，不替代 Y900 真机的 WebView、密度、系统栏和进程恢复验收。
